# 06 — Performance strategy

## 1. Principle

Performance is a product requirement, not an optimization phase. But **no arbitrary target is presented as a guarantee**: budgets are set after the first measurement campaign, then maintained.

Three rules:

1. **Measure before optimizing.** Every structural optimization cites a scenario, a before/after measurement, and a profile.
2. **Measure real usage.** The number of commits is only one dimension among others.
3. **Protect gains.** A budget that is met becomes a regression test.

## 2. Scenarios

| ID | Scenario | Main metrics | Corpus |
|---|---|---|---|
| PERF-01 | Cold repository opening | time to first page, time to interaction, RSS | 10k / 100k / 1M commits |
| PERF-02 | Initial graph display | first-page time, fps, memory | same + many refs |
| PERF-03 | Continuous scrolling | p50/p95 frame time, missed frames, memory | 100k commits, many lanes |
| PERF-04 | Many branches and merges | ref load time, fps, memory | 5k branches, merge history |
| PERF-05 | Large number of files | status time, memory, list fps | 50k / 200k files |
| PERF-06 | Working tree status calculation | cold and warm p50/p95 | 10k / 100k modified files |
| PERF-07 | Partial staging | round-trip latency, consistency | many hunks, large files |
| PERF-08 | Large diff | time to first hunk, total time, memory | 10k / 50k lines, generated files |
| PERF-09 | Rapid repository switching | switching time, peak RSS, leaks | 5 repositories opened alternately |
| PERF-10 | Fetch and graph refresh | duration, IPC bytes, event frequency | repository with 100 new refs |
| PERF-11 | Idle repositories | CPU %, RSS, wakeups | 5 open repositories, 10 min |
| PERF-12 | Commit search | first-page time, p95 | 1M commits |

Each scenario defines: preparation, action, measurement, expected status, noise threshold.

## 3. Corpus

### Synthetic (required, versioned)

Generated by a deterministic script (`crates/bench` or `scripts/corpus.sh`), with a fixed seed:

| Corpus | Content |
|---|---|
| `linear-10k` | 10,000 commits, one growing file |
| `linear-100k` | 100,000 commits |
| `linear-1m` | 1,000,000 commits, used only in nightly runs |
| `branches-5k` | 5,000 branches, remote refs, tags |
| `merges-deep` | binary merge tree, depth 1,000 |
| `merges-octopus` | 8-parent merges |
| `wide-200k` | 200,000 files spread across deep directories |
| `dirty-10k` | 10,000 modified/staged/untracked files |
| `diff-50k` | one modified 50,000-line file |
| `binary-large` | 1 / 50 MiB binary files |
| `crlf-unicode` | mixed line endings, Unicode paths, missing newline |
| `worktrees` | 5 worktrees sharing a common dir |

Generated objects are not committed to the application repository; only the generator, seeds, and metadata are.

### Real (optional)

- Representative internal repositories, used with permission and without sensitive data.
- The report records only metrics and repository size, never paths or messages.
- The absence of a real repository does not block the campaign.

## 4. Methodology

1. `release` build with profiling symbols.
2. Documented reference machine (CPU, RAM, disk, OS, Git version).
3. 3 warm-up runs, then 10 measurements.
4. Report: median, p95, min, max, standard deviation; outliers explained.
5. Comparisons are made **on the same machine**, between two builds.
6. Frontend measurements use a scripted scenario (opening, programmatic scrolling, selection), not human interaction.
7. Rust measurements use `criterion` for parsers and topology.
8. No result is published without the build version, OS, and Git version.

## 5. Budgets

### Step 1 — baseline

The first P0 campaign produces the figures. They become the reference.

### Step 2 — product budgets

Budgets are set per scenario after the baseline, with an explicit margin. Example format:

| Scenario | Provisional budget `[HYPOTHESIS]` | Decision |
|---|---|---|
| PERF-01 opening 100k commits | first page < 500 ms | to be replaced by the baseline |
| PERF-01 opening 1M commits | first page < 1.5 s | nightly only |
| PERF-03 scrolling | p95 frame < 16.7 ms, no frame > 50 ms | to be validated |
| PERF-05 status 100k files | warm < 400 ms | to be validated |
| PERF-07 staging | round trip < 150 ms | measured 35.3 ms p50 / 48.5 ms p95 (dirty-10k, 2026-10-27) |
| PERF-08 diff 50k lines | first screen < 200 ms | to be validated |
| PERF-09 repository switching | < 600 ms | to be validated |
| PERF-10 fetch + refresh | < 250 ms p95 (local remote, 10k commits) | measured 87.2 ms p50 / 98.6 ms p95 (2026-10-27) |
| PERF-11 idle repositories | CPU < 2%, RSS < 400 MB | to be validated |

These values are **working hypotheses**, not commitments. They are replaced as soon as the first measurement is available and must not be cited as guarantees.

### Step 3 — CI guardrails

- Regression = exceeding `max(absolute budget, baseline × 1.20)` on the median, or `× 1.30` on p95.
- A guardrail failure blocks the merge unless there is a documented justification and a baseline update.
- 1M-commit benchmarks run nightly, not on every PR.

## 6. Instrumentation

### Backend

- `tracing` span per command: `repo_id`, `subcommand`, `duration_ms`, `exit_code`, `stdout_bytes`, `stderr_bytes`.
- Counters: Git invocations, IPC bytes, cache entries, invalidations.
- Measurement of each phase: reading, parsing, topology calculation, serialization.

### Frontend

- `performance.mark` / `measure`: `app.start`, `repo.open`, `graph.first-page`, `graph.first-paint`, `diff.first-paint`.
- Frame timing via `requestAnimationFrame` (p50/p95, frames > 50 ms).
- Memory: `performance.memory` if available, otherwise RSS through the backend.
- No measurements sent over the network.

## 7. Graph rendering

Framework-independent design constraints:

1. **Canvas**, not one DOM node per commit.
2. Fixed row height; only visible rows + overscan are drawn.
3. Topology and lanes calculated on the Rust side from parents; the frontend draws segments.
4. Pagination with a growing window; incremental appending without full recalculation.
5. No layout recalculation on scroll; no sorting on every frame.
6. Colors per lane, grouped refs, optional avatars (measured cost).
7. “All branches” mode is an explicit choice, never the default on large repositories.
8. A selection does not trigger diff loading beyond the cap.

Lane algorithm (summary):

- maintain a table of active lanes;
- for each commit, find its first child's lane, close the other parents' lanes, open new ones;
- bytes/segments produced per page, independent of the total number of commits;
- tests on merges, octopus, dead branches, nonlinear history.

## 8. IPC

- Pages of 500 commits by default, adaptive size to stay below 1 MiB.
- No diff in the log page.
- Coalesced progress events (max ~10/s).
- Targeted invalidations (`refs`, `index`, `worktree`), not global ones.
- Byte measurement per scenario; if volume becomes a bottleneck, a binary format may be considered — measurement-based decision.

## 9. Cache and invalidation

| Cache | Key | Invalidation | Bound |
|---|---|---|---|
| Refs | repo + generation | ref mutation, watcher | small |
| Log | repo + cursor + filters | new ref, fetch | recent pages |
| Status | repo + generation | watcher, mutation | one entry |
| Diff | repo + shas + path | mutation | LRU |
| Topology | repo + page | new page | per session |
| GitLab | endpoint + params + ETag | TTL, mutation | LRU |

- No global invalidation except on repository or token change.
- The watcher uses a 150 ms debounce and ignores irrelevant internal files (`objects/`, `logs/`).
- An external change invalidates the affected areas, not the entire repository.

## 10. Optimization order

1. Remove full loads and blocking waits.
2. Virtualize lists and the graph.
3. Reduce IPC volume.
4. Fix cache invalidation.
5. Move expensive calculations (topology, parsing) to Rust.
6. Optimize rendering (offscreen canvas, batches, buffer reuse).
7. Consider `gix` for targeted reading, only with evidence.

Each step must be justified by a profile. No “just in case” optimization.

## 11. Performance tests

| Level | Tool | Frequency |
|---|---|---|
| Parsers / topology | `criterion` | PR |
| Application scenarios | `crates/bench` harness | PR (reduced corpus), nightly (full) |
| Frontend | scripted scenario + frame timing | PR (smoke), nightly |
| Memory / idle | OS measurement over 10 min | nightly |
| Regression | baseline comparison | PR |

A performance test that measures only an average is invalid: p95 and missed frames are required for the UI.

## 12. P3 optimization — graph pagination

**Scenario:** PERF-03, appending 10 pages of 500 commits.
**Cause:** `--skip=<n>` cursor: each page rescanned the entire prefix
(≈ 3.8 s/page on 1 M commits).
**Fix:** `RepoSession` keeps a streaming `git log` process; each
page reads the next lines and costs only its `--max-count`. The
cursor becomes `index:sha` and falls back to `--skip` only for
nonsequential access. The process is canceled when the session closes.

| Corpus | Before (p50, 10 pages) | After (p50, 10 pages) | Gain |
|---|---|---|---|
| `linear-100k` | 3,587 ms | 18.3 ms | ≈ 196× |
| `linear-1m` | 38,616 ms | 18.3 ms | ≈ 2,110× |

Local measurements (macOS arm64, Git 2.55.0), report:
`target/bench-p3-before-*.json`, `target/bench-p3-after-*.json`.
The reduced set retains its budgets; PERF-03 is well below the baseline.

### Limitation

The stream keeps one process per active repository session. It is canceled at
session `shutdown` and does not load the full history into memory.
