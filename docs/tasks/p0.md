## P0-T01 — Scaffold workspace, Tauri 2 et CI

**Objectif :** disposer d'une application vide qui se lance sur les trois OS, avec des pipelines verts et des frontières de crates respectées.

**Dépend de :** —

**Livrables**

- Workspace Cargo : `core`, `git`, `gitlab`, `store`, `app`, `bench`.
- Application Tauri 2 minimale avec une fenêtre et une page d'accueil.
- Frontend **React 19.3 + TypeScript + Vite**, build, lint, typecheck.
- Configuration Tauri : CSP restrictive, capabilities minimales.
- Logging structuré (`tracing`), répertoires app data.
- CI : format, clippy `-D warnings`, tests, build, matrice Windows/macOS/Linux.
- Script de fixtures Git (squelette).

**Étapes**

1. Créer le workspace et les crates vides avec les règles de dépendance.
2. Initialiser Tauri 2 et le frontend.
3. Ajouter le logging et la gestion des répertoires.
4. Ajouter la CI et le cache de build.
5. Vérifier le lancement sur les trois OS.

**Critères d'acceptation**

- `cargo build`, `cargo test`, `cargo clippy -- -D warnings` passent.
- Le frontend compile et se lance.
- L'application ouvre une fenêtre sur Windows, macOS et Linux.
- La CSP interdit les scripts distants ; aucune capability inutile.
- Aucun accès réseau au démarrage.

**Tests**

- Smoke test de lancement (CI).
- Test unitaire trivial par crate pour valider la structure.
- Vérification de la matrice CI.

**Hors périmètre**

- Toute fonctionnalité Git ou GitLab.
- Design system.

**Preuve attendue**

- Logs CI verts sur les trois OS ; capture de la fenêtre vide.

## P0-T02 — Couche processus Git

**Objectif :** centraliser toute exécution Git dans un module sûr, observable et annulable.

**Dépend de :** P0-T01

**Livrables**

- `git::process` : `CommandSpec`, résolution du binaire, allowlist de sous-commandes/options.
- Construction argv sans shell.
- Environnement contrôlé (`GIT_TERMINAL_PROMPT=0`, `GIT_PAGER=cat`, etc.).
- Capture bornée de `stdout`/`stderr`, code de sortie, durée.
- Streaming et annulation pour les opérations longues.
- Redaction centralisée.
- `git::capability` : version et options disponibles.

**Étapes**

1. Définir les types et l'allowlist.
2. Implémenter le lancement, la capture et le timeout.
3. Implémenter le streaming et l'annulation (Unix/Windows).
4. Ajouter la redaction et les spans `tracing`.
5. Tests unitaires et intégration sur fixtures.

**Critères d'acceptation**

- Aucune commande ne passe par un shell.
- Un argument contenant des espaces, guillemets ou `;` n'est jamais interprété.
- Une commande longue peut être annulée ; le processus est arrêté.
- La sortie est bornée et les secrets sont redactés.
- Windows n'ouvre pas de console.
- Les erreurs renvoient un code stable.

**Tests**

- Unitaires : construction argv, allowlist, redaction.
- Intégration : `git --version`, `status`, commande annulée, commande en échec.
- Plateforme : annulation sur les trois OS.

**Hors périmètre**

- Commandes métier (status, log, etc.).

**Preuve attendue**

- Tests verts + démonstration d'annulation d'un `fetch` fictif ou d'un `sleep` lancé par un helper de test.

## P0-T03 — Découverte et session de dépôt

**Objectif :** ouvrir un dépôt ou un worktree, connaître son état, et maintenir une session cohérente.

**Dépend de :** P0-T02

**Livrables**

- Découverte : worktree, git dir, common dir, bare, inside-worktree.
- `RepoSession` : identifiant, chemins, génération, état, file de mutations.
- Détection de l'état : merge, rebase, cherry-pick, revert, bisect, conflits, détaché, non-né, verrous.
- Watcher avec debounce et invalidation ciblée.
- Registre des sessions et fermeture propre.

**Étapes**

1. Implémenter la découverte et la validation de chemin.
2. Implémenter la détection d'état via `rev-parse --git-path` et `status`.
3. Implémenter la file de mutations et la génération.
4. Implémenter le watcher et l'invalidation.
5. Tests sur fixtures (worktree, submodule, états intermédiaires).

**Critères d'acceptation**

- Ouvrir un dépôt, un worktree et un submodule produit la bonne session.
- Les états intermédiaires sont détectés correctement.
- Une modification externe invalide les zones concernées.
- La fermeture ne laisse ni watcher ni processus.
- Un chemin invalide renvoie `repo.not_git`.

**Tests**

- Fixtures : dépôt simple, worktrees, submodule, merge en cours, rebase, detached, bare.
- Test de fermeture et de fuite de ressources.
- Test de modification externe.

**Hors périmètre**

- UI complète ; lecture de l'historique.

**Preuve attendue**

- Rapport de tests sur les fixtures + journal des invalidations.

## P0-T04 — Modèle de lecture

**Objectif :** fournir au frontend les données nécessaires au graphe, au status et au diff, avec pagination et types stables.

**Dépend de :** P0-T03

**Livrables**

- Refs : branches locales/distantes, tags, remotes, upstream, HEAD.
- Status : parsing `--porcelain=v2 -z`, conflits, untracked.
- Log : page de commits avec parents, auteur, date, refs, sujet.
- Détail de commit : message, fichiers, stats.
- Diff : parseur unifié, hunks, binaire, absence de newline.
- DTO sérialisés et versionnés.

**Étapes**

1. Implémenter les parseurs avec tests unitaires.
2. Implémenter les commandes et les DTO.
3. Ajouter la pagination et les plafonds.
4. Brancher les commandes Tauri de lecture.
5. Mesurer les temps de chaque lecture (entrée pour P0-T08).

**Critères d'acceptation**

- Les données sont correctes sur toutes les fixtures.
- Aucune commande ne charge tout l'historique ou tous les fichiers implicitement.
- Une lecture obsolète est identifiable par sa génération.
- Les cas binaires, renommages, CRLF et Unicode sont gérés.
- Les erreurs sont typées.

**Tests**

- Unitaires : chaque parseur, cas limites.
- Intégration : commandes sur fixtures, comparaison avec `git` en ligne de commande.
- Contrat : formes des DTO.

**Hors périmètre**

- Rendu UI ; interactions.

**Preuve attendue**

- Tableau des temps de lecture + tests verts.

## P0-T09 — Erreurs et reprise

**Objectif :** rendre les échecs compréhensibles et les états intermédiaires récupérables.

**Dépend de :** P0-T02, P0-T03

**Livrables**

- `AppError` et taxonomie.
- Mapping des erreurs Git connues.
- Journal d'opérations SQLite.
- Détection des opérations interrompues au démarrage.
- Panneau de reprise.
- Redaction des détails.

**Étapes**

1. Définir les codes et catégories.
2. Implémenter le mapping et les tests.
3. Implémenter le journal.
4. Implémenter la reprise et le panneau.
5. Fault injection.

**Critères d'acceptation**

- Chaque erreur connue a un code stable et une remédiation.
- Un kill pendant une opération est détecté au redémarrage.
- Aucun verrou n'est supprimé automatiquement.
- Aucune erreur n'est silencieuse.
- Les détails sont redactés.

**Tests**

- Kill pendant fetch/commit/rebase.
- Vérification des artefacts.

**Hors périmètre**
